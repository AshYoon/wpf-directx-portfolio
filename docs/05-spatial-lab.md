# Spatial Lab v0.2 구현 기록

## ATTS에서 참고한 범위

공통적인 WPF/Win32 연동 구조인 HwndHost의 네이티브 자식 창 생성, DLL 호출,
네이티브 렌더러를 창보다 먼저 해제하는 수명 관리 방식을 참고했습니다.
업무 구조체·함수·도메인 모델·회사 UI·에셋을 복사하지 않았습니다.

초기 버전의 질문은 “같은 원 범위 검색을 전체 순회와 공간 그리드로 실행하면
정답과 후보 수, 유지 비용이 어떻게 달라지는가?”입니다.

## 데이터와 알고리즘

100×100 월드에서 점 객체가 이동합니다. 그리드는 한 변 5인 셀 20×20개입니다.
객체 ID는 벡터 인덱스이며 개체 재생성 전까지 유지됩니다.
모든 객체는 하나의 셀에만 속합니다.

전체 순회는 모든 객체에 제곱 거리 검사를 합니다.
그리드 검색은 검색 원의 경계 사각형이 걸치는 셀을 순회하고,
후보마다 같은 제곱 거리 검사를 합니다.
원의 경계에 정확히 닿는 점도 결과에 포함합니다.
월드의 100 좌표는 마지막 셀에 포함합니다.

그리드의 검색 비용은 방문 셀 수와 후보 수에 따라 달라집니다.
고정된 상수 시간이나 무조건적인 성능 향상을 주장하지 않습니다.
현재는 움직이는 장면의 그리드를 매 프레임 전체 재구성하므로
재구성 비용은 객체 수와 셀 수의 영향을 받습니다.

## WPF와 네이티브 경계

- Windows x64 / cdecl / 고정 크기 C 구조체 / signed HRESULT.
- Settings 32 bytes, Stats 72 bytes. 양쪽에서 크기를 확인합니다.
- 설정 구조체는 호출 중 복사하며 native 포인터를 UI 모델로 노출하지 않습니다.
- 네이티브 예외는 HRESULT로 바꿔 C 경계 밖으로 전파하지 않습니다.
- 생성 스레드 이외의 직접 핸들 호출을 거절합니다. 후속 이식의 `SR_Enqueue*`는 명령 접수만 허용합니다.
- WPF는 별도의 렌더 스레드 없이 UI 스레드에서 호출합니다.
- HwndHost가 자식 HWND를 소유하고 Renderer가 GPU 자원을 소유합니다.
- DirectX COM 자원은 ComPtr로 관리합니다.
- ABI v1 골격에 Configure/SetQuery/GetStats/CopyFrame을 추가해 v2가 됐습니다.

## 화면과 입력

DirectX 화면은 정사각 월드가 창의 종횡비와 무관하게 유지되도록 투영합니다.
네이티브 자식 창의 실제 픽셀 크기로 swap chain과 viewport를 갱신합니다.
클릭·드래그 좌표는 동일한 투영의 역변환으로 월드에 대응시키며,
월드 밖의 입력은 가장자리로 제한합니다.
WPF 패널은 HwndHost 영역과 겹치지 않습니다.

## 측정과 검증

두 검색은 같은 프레임의 같은 객체 배열을 사용합니다.
그리드 결과를 정렬한 뒤 전체 순회 결과와 비교하며 이 검증 비용은 검색 시간에서 제외합니다.
설정 직후의 진단 캡처도 최신 검색 결과를 사용합니다.
캡처는 시뮬레이션을 이동시키지 않습니다.

실시간 수치는 설명용 단일 호출 측정입니다.
별도 CLI 벤치마크는 동일 스냅샷에서 64개 범위 검색을 묶고,
워밍업 이후 15회 측정의 중앙값을 표시합니다.
메서드 실행 순서를 번갈아 바꿉니다. 프레임 렌더링 성능 측정은 아닙니다.

## 현재 한계와 다음 후보

- 점 객체·평면 월드만 지원합니다. 충돌 메시/BVH/3D 모델/게임플레이 AI는 없습니다.
- 그리드는 전체 재구성 방식입니다. 변경된 셀만 갱신하는 최적화는 하지 않았습니다.
- 프레임 요청과 DirectX 호출은 UI 소유 스레드에서 수행합니다. 후속 CPU 검색 병렬화에서도 완료를 기다리므로 무거운 작업은 WPF 반응성에 영향을 줄 수 있습니다.
- 원자적 핸들 registry를 두지 않아 파괴된 핸들 재사용은 금지된 API 사용입니다.
- 새로운 기능보다 수동 조작, 다른 DPI, 장시간 실행 확인이 우선입니다.

후속 C++ 명령 큐·작업 풀 이식 내용은 [네이티브 스레딩 이식](09-native-threading-port.md)을 참고하세요.
